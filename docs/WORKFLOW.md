# Workflow

## สถานะกิจกรรม (`apps/api/src/events/event-state.ts`)

```text
DRAFT ──submit──▶ PENDING_APPROVAL ──(ทุกขั้นอนุมัติ)──▶ APPROVED ──publish──▶ PUBLISHED
  ▲                    │  return (DRAFT + approval RETURNED)          │
  │                    │  reject  ──▶ REJECTED ──submit อีกครั้ง─┘      ├─open──▶ REGISTRATION_OPEN ──close──▶ REGISTRATION_CLOSED
  └────────────────────┘                                              │                                     │ (reopen ได้)
                                                                      └──────start──────────────────────────┴──▶ IN_PROGRESS ──complete──▶ COMPLETED
ทุกสถานะ (ยกเว้น COMPLETED) ──cancel (ระบุเหตุผล)──▶ CANCELLED  (ยกเลิกการลงทะเบียนที่ยังใช้งานทั้งหมด)
```

- สถานะกิจกรรม / สถานะอนุมัติ (`approval_status`) / สถานะลงทะเบียน แยกกัน
- **เปิดรับสมัครอัตโนมัติ**: PUBLISHED + มี `registration_open_at` → รับสมัครภายใน [open, close) โดยไม่ต้องมี job
- แก้ไขทั้งหมดได้เฉพาะ DRAFT/REJECTED; หลังอนุมัติแก้ได้เฉพาะรายละเอียดทั่วไป จำนวนรับ (ไม่ต่ำกว่าที่นั่งที่ใช้) แท็ก — เปลี่ยนวันเวลาต้อง "เลื่อนกำหนดการ" (บันทึกประวัติ + เหตุผล)
- ทุกการเปลี่ยนสถานะบันทึก `event_status_history` (append-only) และ `audit_logs`

## Workflow อนุมัติ
1. ผู้จัดกด "เสนออนุมัติ" → เลือก workflow: ของหน่วยงานที่ใกล้ที่สุดในสายบังคับบัญชา → ถ้าไม่มีใช้ค่ากลาง (`DEFAULT`)
2. ขั้นที่ `paid_events_only` (ตรวจการเงิน) ข้ามเมื่อกิจกรรมไม่มีค่าใช้จ่าย
3. ผู้อนุมัติแต่ละขั้น: อนุมัติ / ไม่อนุมัติ (ต้องมีเหตุผล) / ส่งกลับแก้ไข (ต้องมีเหตุผล)
4. ผู้เสนอและผู้สร้างกิจกรรมพิจารณาเองไม่ได้; ขั้นหนึ่งพิจารณาได้ครั้งเดียว (optimistic guard)
5. ประวัติทุกขั้นใน `approval_actions` (append-only) — ยื่นใหม่เป็น round ใหม่
6. (P2) แก้ค่าลงทะเบียนหลังเผยแพร่ → สร้าง request `trigger = FEE_CHANGE`

Workflow เริ่มต้น (seed): ① หัวหน้าหน่วยงานผู้จัด → ② กองคลังตรวจอัตรา/บัญชีรับเงิน (เฉพาะมีค่าใช้จ่าย) → ③ ผู้อนุมัติส่วนกลาง

## การลงทะเบียน
```text
ส่งแบบฟอร์ม (Idempotency-Key) ─▶ ล็อกกิจกรรม ─▶ ที่นั่งพอ? ─ใช่─▶ CONFIRMED (กิจกรรมฟรี) / PENDING_PAYMENT (P2)
                                              └─ไม่─▶ เปิดสำรอง? ─ใช่─▶ WAITLISTED  ─ไม่─▶ 409 EVENT_FULL
ยกเลิก ─▶ คืนที่นั่ง ─▶ เลื่อนผู้สำรองตามลำดับ (FIFO) ใน transaction เดียวกัน
```
ผู้ไม่เข้าสู่ระบบได้รับ "ลิงก์ตรวจสอบสถานะ" (token อยู่ใน URL fragment ไม่ถูกส่งไปเซิร์ฟเวอร์/log) ใช้ตรวจหรือยกเลิกได้

## การลงทะเบียนแบบกลุ่ม (P3)
```text
ผู้ประสานงานสร้างองค์กร ─▶ สร้างกลุ่ม (DRAFT, ไม่ถือที่นั่ง)
   ├─ เพิ่มสมาชิกเอง / ลิงก์เชิญแบบเปิด (สมาชิกกรอกเอง + ยินยอม PDPA เอง) / นำเข้า Excel (ตรวจ → ดูตัวอย่าง → ยืนยัน)
   └─ ส่งกลุ่ม (ยืนยันว่าได้รับความยินยอมจากสมาชิก)
        ─▶ ล็อกกลุ่ม → ล็อกกิจกรรม → ตรวจ min/max, ข้อมูลครบ, อีเมลซ้ำ, ที่นั่งพอทั้งกลุ่ม?
             ├─ไม่พอ─▶ 409 GROUP_SEATS_UNAVAILABLE (ไม่จองบางส่วน ไม่เข้าคิวสำรอง)
             └─พอ──▶ seats_taken += n ─▶ สมาชิกได้เลข REG- ─▶ ฟรี: CONFIRMED / มีค่าใช้จ่าย: PENDING_PAYMENT + ใบแจ้งชำระรวม 1 ใบ
ชำระ/ยกเว้น/รับเงินสด ─▶ กลุ่มและสมาชิกทุกคน CONFIRMED      เลยกำหนด ─▶ ทั้งกลุ่ม EXPIRED คืนที่นั่ง เลื่อนผู้สำรอง
```
- **หลังส่งกลุ่ม** (ก่อน `memberChangeCloseAt` หรือเวลาเริ่มกิจกรรม): เปลี่ยนตัว/แก้ข้อมูลได้เสมอ (ต้องมีเหตุผล, ที่นั่งและค่าลงทะเบียนเดิม) · เพิ่ม/ถอนได้เฉพาะเมื่อยังไม่ชำระ (หรือกิจกรรมฟรี) → ยกเลิกใบแจ้งเดิมและออกใบใหม่ด้วยกำหนดชำระเดิม (สมาชิกเดิมคงอัตราเดิม สมาชิกใหม่ใช้อัตรา ณ ขณะนั้น) · ระหว่างรอตรวจสลิปห้ามเพิ่ม/ถอน
- **ยกเลิกกลุ่ม**: สมาชิกทั้งหมด CANCELLED คืนที่นั่ง เลื่อนผู้สำรอง; ใบแจ้งที่ยังไม่ชำระ → CANCELLED, ชำระแล้ว → REFUND_PENDING (กระบวนการคืนเงิน P2b) · ยกเลิกกิจกรรม → ยกเลิกทุกกลุ่ม
- สมาชิกกลุ่มยกเลิกรายคนผ่านหน้ารายบุคคลไม่ได้ (`GROUP_MEMBER`) — ต้องผ่านผู้ประสานงาน
- ทุกการเปลี่ยนแปลงบันทึก `group_change_logs` (append-only) + `audit_logs`; ผู้ตรวจสลิป/ยกเว้นค่าธรรมเนียม/รับเงินต้องไม่ใช่ผู้ประสานงานของกลุ่ม (SoD)

## เช็กอินและการเข้าร่วม (P4)
```text
ผู้เข้าร่วม (CONFIRMED) ─▶ QR จาก "ประวัติการลงทะเบียน" / ลิงก์ตรวจสถานะ / ป้ายชื่อ   (กลุ่ม: QR กลุ่มที่หน้าผู้ประสานงาน)
จุดเช็กอิน: กล้อง / เครื่องสแกน (keyboard wedge) / ค้นชื่อ ─▶ scan
   ├─ QR กลุ่ม ─▶ รายชื่อสมาชิก ─▶ เลือกคนที่มาถึง ─▶ เช็กอินพร้อมกัน
   └─ ล็อกแถวการลงทะเบียน ─▶ ตรวจ: สถานะกิจกรรม, ช่วงเวลาเช็กอิน, ลงทะเบียน CONFIRMED
         ├─ รอชำระ ─▶ PAYMENT_PENDING (ส่งไปจุดรับชำระ) · สำรอง/ยกเลิก ─▶ ปฏิเสธ
         ├─ เคยเช็กอินในขอบเขตเดียวกัน ─▶ ALREADY_CHECKED_IN (ไม่บันทึกซ้ำ แม้สแกนพร้อมกันหลายจุด)
         └─ บันทึก CHECK_IN ─▶ คำนวณการเข้าร่วม (ช่วงกิจกรรม + ทั้งกิจกรรม; มาสายถ้าเกินเวลาที่ตั้ง) ─▶ แจ้ง real-time ─▶ (ตัวเลือก) พิมพ์ป้ายทันที
สแกนผิดคน ─▶ UNDO (ต้องมีเหตุผล) ─▶ คำนวณการเข้าร่วมใหม่
ออฟไลน์ ─▶ ตรวจ QR กับรายชื่อในเครื่อง (hash) ─▶ คิวในเครื่อง ─▶ ออนไลน์แล้ว sync (clientKey กันซ้ำ, เวลา = เวลาที่สแกนจริง)
```
- ช่วงเวลาเช็กอิน: `start_at − checkin_opens_before_minutes` ถึง `end_at` (ตั้งได้ต่อกิจกรรม)
- ขอบเขตกันซ้ำ: จุดที่ผูกช่วงกิจกรรม → ซ้ำภายในช่วงนั้น; ไม่ผูก → ทั้งกิจกรรม (เข้าช่วงใดช่วงหนึ่งแล้วถือว่าเข้าร่วมกิจกรรม)
- เจ้าหน้าที่ปรับสถานะการเข้าร่วมด้วยมือได้ (เข้าร่วม/มาสาย/ลา/ไม่เข้าร่วม) พร้อมเหตุผล → audit; การสแกนจริงภายหลังทับค่า
- ผู้ใช้ที่ถูกเพิ่มเป็น "บุคลากรของงาน" และเปิด "เปิดจุดเช็กอินได้" ใช้สิทธิ์เช็กอินของตนได้เฉพาะกิจกรรมนั้น

## ป้ายชื่อ (P4)
- แม่แบบต่อกิจกรรม: ข้อความ (ตัวแปร `{fullName}` ฯลฯ), แถบสีตามกฎ (ประเภทผู้เข้าร่วม / บทบาทบุคลากร / ทุกคน), QR เช็กอิน, ภาพพื้นหลัง — A4 หลายป้ายต่อแผ่น (เลือกแนวที่ได้มากสุด มีเส้นตัด) หรือ 1 ป้ายต่อหน้าสำหรับเครื่องพิมพ์บัตร/ฉลาก
- พิมพ์ชุด (ตามตัวกรอง/ที่เลือก, ข้ามคนที่พิมพ์แล้ว) · พิมพ์ทันทีที่จุดเช็กอิน (แม่แบบหลัก) · พิมพ์ซ้ำ: ต้องมี `badge:reprint` + เหตุผล, ป้ายมีเครื่องหมาย "พิมพ์ซ้ำ #n"
- ทุกป้ายที่พิมพ์ = แถว `badge_prints` (ครั้งที่, ผู้สั่ง, เวลา); งานพิมพ์เก็บ snapshot แม่แบบ การเปิดไฟล์ซ้ำนับจำนวนและบันทึก audit

## แบบประเมินและเกียรติบัตร (P5a)
```text
ผู้จัด: สร้างแบบประเมิน (ชุดคำถามมาตรฐาน) ─▶ ปรับ ─▶ เผยแพร่ ─▶ (เปิดตอบเมื่อกิจกรรมเริ่ม หรือเวลาที่ตั้ง) ─▶ ปิดรับ
ผู้เข้าร่วมที่เช็กอินแล้ว ─▶ /my/evaluations หรือหน้าตรวจสถานะ (guest) ─▶ ตอบได้ครั้งเดียว
ผู้จัด: แม่แบบเกียรติบัตร + เกณฑ์ ─▶ ตรวจรายชื่อ (ผ่าน/ไม่ผ่าน พร้อมเหตุผล)
   ├─ ออกให้ทุกคนที่ผ่านเกณฑ์ / ที่เลือก / ยกเว้นเกณฑ์ (มีเหตุผล → audit)
   └─ เปิดให้รับเอง ─▶ ผู้เข้าร่วมผ่านเกณฑ์ ─▶ "รับเกียรติบัตร" ─▶ PDF
เกียรติบัตร ─▶ QR / รหัส 12 หลัก ─▶ /verify/<รหัส> (ใช้ได้ / ยกเลิกแล้ว / ไม่พบ)
แก้ข้อมูลผิด ─▶ ยกเลิก (เหตุผล) ─▶ ออกฉบับใหม่ (เลขที่ใหม่)
```
- เกณฑ์ของแม่แบบผู้เข้าร่วม: ลงทะเบียน CONFIRMED · เช็กอิน (นับมาสายหรือไม่) · เข้าช่วงกิจกรรม ≥ n% (เฉพาะกิจกรรมที่มีช่วง) · ตอบแบบประเมินที่ "ใช้เป็นเงื่อนไขรับเกียรติบัตร" ครบ — "ลา" ไม่นับว่าเข้าร่วม
- ออกได้เมื่อกิจกรรมเริ่มแล้วและไม่ถูกยกเลิก; แก้แม่แบบภายหลังไม่กระทบฉบับที่ออกแล้ว (snapshot)

## การจองสถานที่และอุปกรณ์ (P5b)
```text
ผู้ขอ (ผู้จัดกิจกรรม / บุคลากร) ─▶ ดูตารางว่าง ─▶ ขอจอง (ผูกกิจกรรม หรือระบุวัตถุประสงค์)
   ├─ ห้องอนุมัติอัตโนมัติ + ว่าง ─▶ APPROVED ทันที
   ├─ ช่วงเวลามีรายการอนุมัติแล้ว ─▶ VENUE_CONFLICT / RESOURCE_UNAVAILABLE (ไม่สร้างคำขอ)
   └─ PENDING ─▶ แจ้งผู้อนุมัติของหน่วยงานผู้ดูแล ─▶ อนุมัติ (ฐานข้อมูลกันซ้อนอีกชั้น) / ไม่อนุมัติ (มีเหตุผล) ─▶ แจ้งผู้ขอ
ยกเลิกกิจกรรม ─▶ การจองของกิจกรรมทั้งหมดเป็น CANCELLED
```
- คำขอที่ซ้อนกันรอพิจารณาพร้อมกันได้ — รายการที่ได้รับอนุมัติก่อนได้สิทธิ์ อีกรายการอนุมัติไม่ได้ (ไม่อนุมัติหรือให้ผู้ขอเปลี่ยนเวลา)

## การแจ้งเตือน (P5b)
```text
ธุรกรรม (ลงทะเบียน / ชำระเงิน / อนุมัติ / ยกเลิก / เลื่อน / จอง / ออกเกียรติบัตร / เปิดแบบประเมิน) ─▶ audit_logs (ใน transaction เดียวกัน)
worker ทุก 20 วินาที ─▶ dispatcher อ่าน audit ที่ commit แล้ว ─▶ หาผู้รับ ─▶ แม่แบบ ─▶ in-app + outbox (อีเมล/LINE ตามการตั้งค่า)
                   ─▶ ส่ง outbox (เช่าแถว, ล้มเหลว → ลองใหม่ 1, 2, 4, 8 นาที … สูงสุด 5 ครั้ง → FAILED ส่งใหม่ได้จากหน้าผู้ดูแล)
                   ─▶ ทุก 10 นาที: เตือนผู้ลงทะเบียนที่ยืนยันแล้วก่อนวันงาน 24 ชั่วโมง (ครั้งเดียวต่อการลงทะเบียน)
เชื่อม LINE: ขอรหัส 8 หลักที่ /my/notifications ─▶ ส่งรหัสในแชตบัญชี LINE ทางการ ─▶ webhook ผูกบัญชี
```
- ผู้ลงทะเบียนแบบ guest ได้รับทางอีเมลเท่านั้น; สมาชิกกลุ่มไม่ได้รับรายคนตอนสร้าง (ผู้ประสานงานแจ้งเอง)
